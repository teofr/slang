NatSpec Lexing Benchmarks

Every optimization tried around PR 2255, each with an ID, and every combination of them measured on main and on PR 2255. All numbers are the geometric mean of the parser stage's instruction count over 9 contracts. Negative is faster.

Summary

  • Best on main: 1c + 4, −3.20%. Best on PR 2255: 1b + 2c + 3 + 4, −3.17% against main. The two are level, so PR 2255's design costs nothing once both sides get the same optimizations.
  • 0 alone costs +2.20%. Most of that goes away with lexer skipping (1a / 1b / 1c), which is also the biggest single win on either base.
  • 4 depends on the reader. It helps main's token loop and the PR's own outlined reader 2c, is what makes 2b pay off, and slightly hurts the pending field 2a.
  • Recommended split (see the review): PR A = 1c + 4 on main (−3.20%); PR B = 0 + 1b gap merge + 2c + 3 on top (±0.0%).
  • Lexer skipping has a design cost. The lexer stops returning every character of the source, which works against the plan to put trivia in the CST. Treat it as temporary.

Method

  • slang_v2 gungraun suite (Callgrind and DHAT), one dry run per branch on GitHub's ubuntu-24.04 runners, numbers taken from each job's log.
  • 54 benchmarks: 6 pipeline stages × 9 contracts. Only the parser stage times parsing; the others parse in setup and moved by at most 0.006%. No variant changed allocations.
  • Instruction counts are deterministic; PR 2255's base and main match to ±0.005% on the parser stage, which sets the noise floor. Estimated cycles come from a cache model that is sensitive to code layout, so quote instructions.
  • Parser tests and all 812 CST and binder snapshots pass on every code branch. Diagnostics snapshots need a solc download that the test environment blocks.
  • Raw logs, parsed metrics and scripts are on bench/2255-results in teofr/slang.

Independent review

Written by a separate Claude agent (Fable) after all results above were in. It read every diff, built the best variants and inspected their generated assembly, without changing the repository or running benchmarks. Its factual claims were re-checked before publishing; one correction is marked below.

Verdict

  • Adopt 0 + 1b's gap merge + 2c + 3, on top of main + 1c + 4. That is the bench/2255-combined-no2-2254 tree, split into two PRs.
  • PR A (performance): 1c + 4 on main, −3.20%. Include validation of the skipped flag (or skip by category), the comment fixes below, a deep-recursion stress test, and a TODO(v2) saying the skipping goes away (or becomes 5d) when trivia enters the CST. Run it with ci:perf.
  • PR B (PR 2255): one lexeme per /// line, merge by source gap, ranges without the trailing line break. Add unit tests for is_line_continuation and write down in the PR body why the merging regex was reverted. Expected ±0.0% on top of A; present it that way, not as "−5.3%".
  • Drop 2a and 2b; fold 4 into PR A. The first review's recommendation of 2a was wrong: its gain came from a compiler inlining heuristic that 4 makes unnecessary.

Correctness

  • 1c is safe on main. Skipping only changes what a match returns, not the patterns, so the lexemes the parser sees are exactly those main's token stream kept. main's /// regex still stops at a blank line, /* */, //// or //. All 12 regular trivia items across the three lexical contexts carry the flag.
  • Possible deep recursion in debug builds. With skipping, logos jumps straight to the next match instead of returning. Release builds turn that into a loop; debug builds may not. On PR 2255 each // line is its own lexeme, so a long comment header could become a very deep chain in debug tests. Add a stress test ("// x\n".repeat(50_000) + "contract C {}"). If it overflows, switch logos to state-machine code generation or merge // lines in the regex again.
  • The skipped flag is unvalidated. Setting it on a NatSpec item would silently drop all documentation. Reject that combination in the definition checks, or skip "every trivia that isn't NatSpec" in code generation. Also remove or document the never-produced lexeme kinds and their 18 unreachable! arms.
  • 2c with 1b is equivalent to the PR's state machine. Checked: CRLF, a lone \r, \n\r, /** after ///, end of file. 2b behaves like 2a; marking per-line reading #[cold] is a slight misnomer for comment-dense files, but harmless.
  • Correction (verified while publishing): the review says the best branch already removed main's second line-break trim. It didn't. That branch is based on PR 2255's base, which predates the trim (memory_safety.rs:70 on main), so the trim still has to be removed when rebasing 3 onto main.

Why 4 helps 2c and hurts 2a

  • As a rule of thumb, one instruction per token is about 0.08% of the parser stage.
  • Without 4: 2a/2b have one next_lexeme call site, so the compiler inlines it. 2c has two and gets neither, paying a call per token. The first review mistook this for a design difference.
  • With 4: the call layer is gone everywhere. 2c's token loop is then minimal. 2b still loads, stores and compares the pending field on every token (about 4 instructions, +0.32%). 2a also pulls the gap check and a jump table into LALRPOP's parsing loop, which raises register pressure across the whole state machine.
  • Robustness. The shape is sound, but two things rest on compiler choices. One #[inline(never)] keeps the comment reader out of the loop. And the token iterator is only inlined into the parsing loop under the release profile's lto = true. That setting is in this repository's .cargo/config.toml, so crates built without LTO likely pay about 1% that the benchmark never sees.
  • The +0.03% parity is a wash, not an identity. The PR is ahead on 6 of 9 contracts, and behind by up to +0.32% on those with more /// lines per token (one_step_leverage_f, multicall3, uniswap).
  • Comment fixes. Explain why 4's #[inline(always)] is there: a second call site stopped the compiler from inlining next_lexeme. And say that the inlining notes on read_natspec_comment describe the compiler's current choice under LTO, not a guarantee.

For the PR reviewer

  1. PR 2255 as filed costs +2.2% on the parser stage, but the cost comes from the call-layer heuristic and from emitting trivia, not from the design. PR A removes both, and PR B is neutral on top.
  2. The inlining comments describe the compiler's current choices under LTO, not guarantees. Add the reasons, and consider 2d so builds without LTO get the same loop.
  3. Merging by source gap doesn't depend on which trivia lexemes exist, so it survives both the skipping and its eventual removal.
  4. The real decision isn't 2a vs 2c. It's whether to build 5d, or give the ~3% back when trivia enters the CST.
